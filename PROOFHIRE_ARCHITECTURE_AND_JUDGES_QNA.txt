PART 1: EXECUTIVE SUMMARY & CORE VALUE PROPOSITION
================================================================================

ProofHire is an autonomous technical vetting engine engineered to solve the "AI Cheat & Resume Hallucination" crisis in software hiring.

The Problem in Modern Hiring:
1. Resumes are filled with inflated buzzwords and generated bullet points.
2. Coding assessments (LeetCode, HackerRank) are easily bypassed using LLMs (ChatGPT, Claude, Copilot).
3. Traditional AI interviewers hallucinate scores, accept generic answers, or can be easily fooled by prompt injection.

ProofHire's Solution:
ProofHire replaces static tests and human resume screening with a unified 5-stage verification loop:
- Stage 1: Multimodal Candidate Ingestion & Knowledge Graph Construction.
- Stage 2: Dynamic, Tailored Engineering Task Generation.
- Stage 3: Asynchronous Heavy AI Code Evaluation (Algorithmic & Edge-Case Vulnerability Analysis).
- Stage 4: Two-Phase Socratic Depth Check (Phase 1: Portfolio Provenance; Phase 2: Live Code Defense).
- Stage 5: Zero-Hallucination Deterministic Judge & Candidate Shortlisting.

--------------------------------------------------------------------------------
KEY DIFFERENTIATOR: THE "ANTI-HALLUCINATION" GUARANTEE
--------------------------------------------------------------------------------
Unlike naive LLM wrappers that ask an AI "Rate this candidate from 1 to 10", ProofHire guarantees integrity through deterministic engineering:
1. Python Math Only: Scores are computed strictly using deterministic arithmetic, bounded penalization rules, and mathematical clamping (0-5).
2. Verbatim Substring Validation: An AI cannot cite evidence unless that exact character sequence appears in the candidate's actual answer.
3. Code-Anchored AST Traversal: Questions quote exact functions, variables, and line numbers from the candidate's GitHub repositories or submitted solution.
4. Token Efficiency: The system does not feed raw 50,000-token resumes into prompts; it extracts a compact subgraph (under 2,000 tokens) using graph traversals.

PART 2: COMPLETE WORKING MECHANISM & DATA FLOW (PLAIN ENGLISH)
================================================================================

Here is how ProofHire works from the moment a candidate applies to the moment a recruiter sees the ranked shortlist:

STEP 1: INTAKE & PROFILE PARSING
- The candidate provides:
  * Name, role title, experience level.
  * Resume text (PDF/Text extraction).
  * GitHub profile URL and/or repository links.
- The backend parses the data into structured entities:
  * Repositories, commits, pull requests, languages, frameworks, claimed accomplishments.

STEP 2: THE MULTIDIGRAPH KNOWLEDGE ENGINE
- ProofHire does NOT dump raw profiles into an LLM context. Instead, it constructs an in-memory NetworkX MultiDiGraph:
  * Node Types: Candidate, Job, Project, Skill, CodeEntity, Claim.
  * Edge Types: USES_LANGUAGE, AUTHORED_COMMIT, CLAIMS_MASTERY, SOLVED_PROBLEM, IMPLEMENTED_IN.
- Graph Pruning & Token Slicing:
  When an AI module asks a question or evaluates an answer, ProofHire queries the graph for the 1-hop or 2-hop neighborhood surrounding the candidate's claimed skills. This reduces prompt payload by ~80% while maximizing factual context.

STEP 3: JOB MATCHING & ENGINEERING CHALLENGE GENERATION
- ProofHire matches the candidate's graph profile against the Job Requirement Schema (e.g., Senior Distributed Systems Engineer).
- It synthesizes a dynamic, realistic engineering task tailored to their level:
  * Includes a scenario brief, architectural constraints, input/output requirements, and an explicit grading rubric.
  * Candidates receive a real-world coding problem rather than an abstract LeetCode puzzle.

STEP 4: CODE SUBMISSION & ASYNCHRONOUS HEAVY AI EVALUATION
- The candidate writes or pastes their solution code into the editor.
- The moment they click "Submit Code":
  1. The code is saved to the backend database and graph node.
  2. The system immediately launches an asynchronous daemon thread running the Heavy AI Model Tier (GPT-5.6 / Gemini 3.5 Pro / Claude Opus tier via LiteLLM).
  3. The Heavy Evaluator performs deep static analysis against the rubric and extracts:
     - Compliance Score (0 to 5).
     - Algorithmic Approach (e.g., streaming generator vs in-memory list).
     - Missing Requirements (unimplemented rubric criteria).
     - Concrete Edge-Case Vulnerabilities (e.g., OOM risk on 1M records, concurrency race conditions, unhandled TypeErrors).
     - Surgical Socratic Probes (targeted questions exposing flaws in their implementation).
  4. The result is cached in SQLite under `sub_eval:{submission_id}`.
  5. While the Heavy Model is analyzing, the user immediately transitions to the interactive Depth Check without waiting.

STEP 5: THE TWO-PHASE SOCRATIC DEPTH CHECK
The Depth Check is a multi-turn, interactive technical interrogation conducted over 6 turns:

* PHASE 1: PORTFOLIO PROVENANCE (Turns 1 to 3)
  - Goal: Validate whether the candidate actually wrote the projects listed on their GitHub and resume, or if they merely copy-pasted a tutorial.
  - Mechanism: ProofHire traverses the Knowledge Graph, picks specific commit hashes, architectural decisions, and libraries from their past repos, and asks probing questions:
    "In your repo 'distributed-cache', you chose an LRU eviction policy with doubly-linked lists. Why didn't you use a segmented hash ring?"
  - If the candidate used ChatGPT to fake their resume, they fail to explain the granular trade-offs of their past code.

* PHASE 2: TASK CODE INTEGRITY & VULNERABILITY DEFENSE (Turns 4 to 6)
  - Goal: Validate whether the candidate understands the code they just submitted for the test.
  - Mechanism: The Depth Check retrieves the background Heavy Evaluator's findings (`sub_eval:{submission_id}`).
  - The Questioner crafts questions directly targeting the candidate's exact lines of code and the vulnerabilities detected by the Heavy AI:
    "In your submission function `process_records`, you stored all unique records in a local `set` and `list`. How will this code behave if the input stream contains 10 million records, and how would you redesign it to prevent an Out-Of-Memory (OOM) crash?"
  - This defeats candidates who pasted a ChatGPT answer into the test: when forced to defend edge-case trade-offs and runtime failures in real-time under Socratic pressure, non-authors collapse.

STEP 6: REAL-TIME VERIFICATION & OBJECTIVE JUDGING
- After every candidate answer:
  1. Verbatim Substring Check: The system searches the candidate's raw response to ensure cited quotes are 100% genuine substrings. Hallucinated quotes from the LLM are stripped.
  2. Deterministic Scoring: An algorithmic scoring engine assesses technical clarity, trade-off awareness, and code ownership.
  3. Risk Flags: If an answer is evasive, off-topic, or factually wrong, deterministic risk flags (`off_topic`, `incorrect`, `unsupported_claim`) are appended.
  4. Visual Diff & Line Markers: The UI displays exact file names, line anchors, and diff snapshots corresponding to the conversation.

STEP 7: CANDIDATE SHORTLIST & HIRING DASHBOARD
- Final overall scores are calculated via deterministic weighting:
  * Final Score = (Graph Profile Match * 0.25) + (Heavy Code Compliance * 0.35) + (Depth Check Defense * 0.40)
- Candidates are ranked with high-contrast UI badges:
  * "STRONG PASS" (Score >= 4.0)
  * "BORDERLINE" (Score 2.5 - 3.9)
  * "FLAGGED / REJECTED" (Score < 2.5 or Critical Risk Flags)
- Recruiters receive a one-click audit trail: every question, answer, diff, detected vulnerability, and verified quote is viewable with zero ambiguity.

Q1: "Why not just run the candidate's code in a Docker container and execute unit tests?"
--------------------------------------------------------------------------------
JUDGE'S SKEPTICISM:
"Standard platforms like LeetCode and HackerRank compile and run code in isolated sandboxes with test suites. Why use an LLM evaluator and Socratic Depth Check instead?"

YOUR WINNING ANSWER:
"Unit test sandboxes only test IF the code passes a set of predefined inputs. They do NOT test if the candidate actually wrote the code, or if the candidate understands architectural trade-offs.
In the age of LLMs, anyone can paste a LeetCode problem into ChatGPT, copy the solution, and pass 100% of the unit tests in a Docker container.
ProofHire solves the real problem: VETTING OWNERSHIP.
1. The Heavy Evaluator analyzes the code like a Principal Staff Engineer conducting a code review: identifying memory scaling limits, race conditions, and design choices.
2. The Two-Phase Depth Check then immediately puts the candidate in the hot seat: asking them why they chose line 12 over an alternative, how their code behaves when RAM is constrained, and how it connects to their past GitHub work.
Passing unit tests proves the code works; ProofHire proves the human knows how and why it works."

--------------------------------------------------------------------------------
Q2: "What if the candidate opens ChatGPT in another tab and pastes ProofHire's Socratic questions into it?"
--------------------------------------------------------------------------------
JUDGE'S SKEPTICISM:
"If a candidate is cheating on the code, won't they just paste your Depth Check questions into ChatGPT to get the answers?"

YOUR WINNING ANSWER:
"They can try, but ProofHire's Socratic Depth Check is specifically engineered to defeat proxy AI generation through three techniques:
1. Micro-Context Grounding: ProofHire's questions do not ask generic textbook definitions like 'What is an LRU cache?'. It asks hyper-specific, multi-variable questions anchored to the candidate's own code diff: 'In line 4 of your submission, you used an in-memory set rather than a streaming generator. How does this affect memory on 10M records?'
2. Cross-Turn Inconsistency Traps: If a candidate uses an external LLM for Turn 1, another prompt for Turn 2, and another for Turn 3, external LLMs lack the holistic state of the candidate's real git history and task context. The Judge detects architectural contradictions between turns.
3. Strict Turn Timers & Reactive Latency: The Depth Check is interactive and paced. A candidate having to read our question, copy it, format context for ChatGPT, wait for generation, and paste it back suffers extreme latency and tone mismatches that trigger our `evasive_response` and `unsupported_claim` risk flags."

Q3: "LLMs are notorious for hallucinating. How do you guarantee the AI doesn't invent bugs or invent high scores?"
--------------------------------------------------------------------------------
JUDGE'S SKEPTICISM:
"How can an enterprise rely on an AI hiring platform when LLMs can hallucinate qualifications, misread code, or make up reasons to fail people?"

YOUR WINNING ANSWER:
"ProofHire enforces strict programmatic anti-hallucination barriers that decouple LLM generation from scoring:
1. Verbatim Substring Enforcement: When the AI cites evidence for why a candidate passed or failed, ProofHire runs a strict Python substring search against the raw transcript. If the exact quoted words do not exist in the candidate's answer, the evidence is discarded.
2. Deterministic Pure-Python Math: The LLM does NOT decide the candidate's final score or ranking. The scores are computed via deterministic Python algorithms with strict bounds, standard deviations, and explicit mathematical penalties for flagged behaviors.
3. AST Grounding: The Questioner is supplied with concrete Abstract Syntax Tree (AST) identifiers (exact function names, class names, imported modules) verified to exist in the submission."

Q6: "What is the difference between Phase 1 and Phase 2 of the Depth Check?"
--------------------------------------------------------------------------------
JUDGE'S SKEPTICISM:
"Why split the Depth Check into two separate phases instead of just asking questions about the test?"
